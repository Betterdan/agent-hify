# Skill: 编码质量标准（通用）

> 语言/框架无关的通用原则。项目特定标准在各项目 `.ai/skills/code-quality-ext.md` 中扩展。

---

## 设计原则

**YAGNI** — 不为假设的未来需求添加功能或抽象
- 三行相似代码优于过早抽象
- 一次性操作不需要 helper 函数
- 不设计不存在的场景的 fallback

**最小变更** — bug 修复不捎带重构，单一职责改动
- 改 A 功能时不顺手调整 B 的代码风格
- 不在 PR 里混入"顺手"的无关修改

**边界验证** — 只在系统边界（用户输入、外部 API）校验
- 内部函数信任调用方，不重复防御性检查
- 框架已保证的约束不再重复验证

---

## 注释原则

**只注释 WHY，不注释 WHAT**
- 写：隐藏约束、特定 bug 的 workaround、反直觉的设计选择
- 不写：描述代码功能的注释（代码本身即文档）
- 不写：多行注释块、大段 docstring

---

## 测试原则

**TDD 顺序** — 先写失败测试，实现让测试通过，重构不破坏测试

**测试隔离** — 单元测试 mock 外部依赖；集成测试用真实依赖（DB/队列）

**测试命名** — 测试名描述行为，不描述实现
- ✅ `test_login_returns_token_on_valid_credentials`
- ❌ `test_authenticate_function`

**覆盖率** — 覆盖率是参考，不是目标；优先覆盖边界/异常路径，而非行覆盖率数字

**跨次运行安全** — 测试不依赖顺序，不依赖残留数据；用随机/唯一 ID 避免数据冲突

---

## 安全原则

**最小暴露** — 错误信息只给用户需要的，内部细节记日志不透传
**依赖最新** — 定期更新依赖，不用已知有漏洞的版本
**超时必须** — 所有 I/O 操作（网络/DB/文件）必须有超时设置
**密钥不进代码** — API Key、密码通过环境变量或密钥管理服务注入

---

## 变更管理

**小步提交** — 每个 commit 是一个可独立理解和回滚的改动
**提交信息** — 描述"为什么"而不是"做了什么"；遵循项目的 commit 格式约定
**不破坏已有接口** — 改功能不破坏已有接口契约；需要 breaking change 时先讨论

---

## 评审分级（通用）

**Critical**（必须修复，阻塞合并）
- 安全漏洞（注入、认证绕过、密钥暴露）
- 数据丢失风险（无事务保护的多步操作）
- 破坏已有功能

**Important**（必须修复）
- 正确性 bug
- 并发安全问题（race condition、TOCTOU）
- 违反项目架构约束
- 所有外部调用无超时

**Minor**（记账本，可延后）
- 命名不清晰
- 测试覆盖低
- 代码重复但不影响正确性
- 注释缺失或多余
