# 行为规范 — 从协作历史提炼

> 这些规则来自真实反馈，优先级高于工具默认行为。

---

## 执行风格

**自主执行，不频繁打断**
- 用户授权后直接执行，不在任务间停下询问"要继续吗"
- 只在真正 BLOCKED（缺少必要信息、有不可逆风险）时才暂停
- 进度汇报在完成后一次给出，不边做边报告

**响应简洁**
- 不在末尾总结"我做了什么"（用户能看 diff）
- 不用过多铺垫（"好的，我来帮你..."）
- 关键信息前置，细节后置

---

## 代码规范

**不过度抽象**
- 三行相似代码 > 过早抽象
- 不为假设的未来需求设计

**不写多余注释**
- 只在 WHY 非显而易见时写注释
- 不写 WHAT 注释（代码本身应当自解释）

**不引入新依赖**
- 技术栈以外的依赖需要先问用户
- 优先用已有的库解决问题

**所有外部调用必须有超时**
- LiteLLM、HTTP 工具调用、MCP 等

---

## 安全规范

**SSE 流式响应不暴露内部错误**
- 异常分支固定字符串 + `logger.error`，不 `str(exc)` 传给客户端
- 历史教训：`str(exc)` 会暴露 SQL 片段、字段名、API key 路径

**DB 并发操作用原子 upsert**
- 用 `pg_insert ... ON CONFLICT DO UPDATE`，不用 read-then-write
- 同文件已有的原子操作模式即规范

---

## 架构纪律

**只走 service 接口跨模块**
- 禁止跨模块 import `repository.py` / `models.py`
- 跨边界只传 Pydantic DTO 或基本类型

**依赖单向**
- 只能依赖更底层模块（见 DESIGN.md §6）
- import-linter 在 CI 强制，变更依赖层时同步更新合约

---

## Git 行为

**提交前核查范围**
- `git status` + `git diff` 确认只提交相关改动
- 不擅自提交与任务无关的文件

**提交信息中文**
- 格式：`type(scope): 中文描述`
- 末尾加 `Co-Authored-By: Claude ... <noreply@anthropic.com>`

---

## 方法论

**SDD 执行时维护进度账本**
- 路径：`.superpowers/sdd/progress.md`
- 每完成一个任务立即追加一行，防止上下文压缩后丢失进度

**评审结果不照单全收**
- Important/Critical 找到，要先核查证据再裁断
- 历史有多次"评审报 Important 实为假阳性"的情况
- 有证据证伪时可驳回；无证据则修复
